# 04. Интеграции и границы гарантий

Автор: Север. 09.11.2026. Все интеграции ниже — проектируемый состав,
не перечень уже поддерживаемых сервисов.

## Две стороны интеграции

**Источник действий:** n8n, Botaqan, ENVERIQ, собственный агент клиента,
SDK TypeScript/Python, MCP-клиент или другая среда исполнения.

**Целевая система:** CRM, почта, календарь, магазин, документы, платёжный API.

Поддержка источника не означает поддержку всех его инструментов. Подключение
MCP не означает проверку бизнес-смысла любой операции произвольного сервера.
Охват публикуется по направлению «источник → версия операции → целевая система».

## Предлагаемый каталог полного коммерческого продукта

| Семейство | Адаптеры для спецификации | Поддерживаемые бизнес-операции |
| --- | --- | --- |
| CRM | HubSpot, amoCRM, Bitrix24 | Контакты, сделки, разрешённые поля, задачи, допустимые переходы |
| Коммуникации | Gmail, Microsoft 365, Slack, Telegram Bot API | Отправка заданному адресату, лимит получателей, вложения, история результата |
| Магазины | Shopify, ENVERIQ API | Заказы, скидки, изменения каталога и доступные операции возврата |
| Рабочие данные | Google Sheets, Calendar, Microsoft Graph | Диапазоны, события, участники, ограничения массового изменения |
| Внутренние API | OpenAPI / typed SDK | Явно описанные операции, схема и эффекты |
| MCP | Поддерживаемые версии транспорта и серверов | Вызовы инструментов, разрешённые ресурсы, управляемая выдача данных |

Каждый адаптер из каталога получает отдельную карточку возможностей.
Доступность OAuth, тарифы провайдера, квоты, scopes и условия распространения
подтверждаются по его документации перед обязательством поддерживать сервис.
Наличие названия в этой концепции не является такой проверкой.

## Три режима контроля

| Режим | Что реально обеспечивается | Что показываем |
| --- | --- | --- |
| Наблюдение | Получение разрешённой телеметрии после/во время действия | «Наблюдаем; блокировка не обеспечивается» |
| Контроль подключённого пути | До исполнения проверяются вызовы через шлюз, обходные доступы не исключены | «Контролируем этот путь; есть непроверенные альтернативы» |
| Обязательный контроль | Для указанного набора операций проверены ключи, серверный доступ и маршрутизация | «Обязательный контроль перечисленных операций», с датой проверки |

Обязательный контроль — результат конфигурации и проверки конкретного
окружения. Он не означает, что скомпрометированный администратор или внешний
провайдер не может совершить действие самостоятельно.

Для браузерного агента с полноценной пользовательской сессией API-шлюз не
контролирует клики в интерфейсе. Нужны отдельные ограничения среды и сетевого
доступа; отсутствие этих ограничений отражается как неполный охват.

## Контракт операции

Каждая версия операции определяет:

1. Идентификатор, провайдера, схему запроса/ответа, разрешённые endpoint и методы.
2. Владельца ресурса и источник его принадлежности клиенту.
3. Эффекты, допустимые поля, чувствительные данные и представление до/после.
4. Необходимые upstream-разрешения и место хранения учётных данных.
5. Предусловия, источник контекста, его свежесть и поведение при недоступности.
6. Поддержку условного изменения, ETag или проверок версии.
7. Idempotency key, срок его действия, дедупликацию и безопасные повторы.
8. Способ сверки результата, внешний request_id и ограничения истории провайдера.
9. Семантику 4xx / 5xx / timeout / частичного успеха.
10. Возможность отмены, компенсации и необратимые последствия.
11. Максимальные размеры, квоты, page/cursor-обход и общий бюджет времени.
12. Известные обходы, остаточные риски и обязательные проверки совместимости.

Нельзя считать timeout доказательством отсутствия эффекта. Нельзя повторять
отправку другим методом только потому, что первый вызов не подтвердился.
При большом пакете нельзя тихо обрезать список и показывать операцию выполненной.

## Денежный пример

Для возврата адаптер читает оплаченный заказ, валюту и уже возвращённую сумму.
Ограничение применяется и к одному запросу, и к накопленным возвратам по заказу.
Согласующий видит реальную сумму и платёжное назначение. Запрос получает
провайдерский idempotency key, если тот поддерживается. После неясного исхода
выполняется сверка статуса, а не слепой повтор.

Если провайдер не позволяет определить результат и безопасно повторить запрос,
это ограничение не скрывается. Для такой операции требуется более строгий режим
и ручное разрешение неопределённого случая.

## MCP

Нужно учитывать discovery, tools/call, resources и другие реально доступные
методы, а не проверять один тип сообщения. Неизвестные методы запрещаются или
получают отдельную опубликованную политику. Фильтрация списка инструментов
улучшает интерфейс, но принудительная проверка выполняется на самом вызове.

Схема и эффект инструмента привязываются к версии. Изменившийся инструмент
не наследует прежнее разрешение автоматически. Описания инструментов и результаты
сервера не могут изменять правила GhostOS. Адреса upstream-серверов проверяются
против SSRF, подмены DNS и неразрешённых перенаправлений.

Долгое согласование не предполагает бесконечного удержания MCP-запроса:
адаптер использует поддерживаемую клиентом механику либо возвращает
структурированное ожидание с action_id. Совместимость тестируется по клиенту и версии.

## Расширения партнёров

SDK адаптера предоставляет строгие типы, проверку схем, тестовый провайдер,
сценарии сбоев и отчёт совместимости. Подпись пакета подтверждает автора,
но не гарантирует корректность кода. Сторонние адаптеры изолируются, получают
минимальные секреты и сетевой доступ, проходят review перед статусом verified.

Маркетплейс не входит в обязательный коммерческий состав: каталог официальных
и проверенных партнёрских адаптеров достаточен для полного продукта.

## Обновление и вывод из поддержки

Фиксация версии, changelog, заранее известный срок прекращения поддержки,
проверка на test и явное продвижение в production. Критическое несовместимое
изменение приостанавливает затронутую операцию. Клиент получает список влияния,
а не общее уведомление «что-то сломалось».
