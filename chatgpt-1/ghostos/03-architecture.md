## 1. Разделение управления и исполнения

```text
Кабинет / API администратора
        ↓
Управление: организации, агенты, правила, согласования, биллинг
        ↓ подписанные версии правил и реестр отзывов
Исполнение: identity → нормализация → контекст → решение → резерв → вызов
        ↓                                                   ↓
Журнал событий / сверка результата                    Внешняя система
```

Панель не хранит долгий браузерный запрос до согласования. Ожидание —
долговечное состояние в БД; агент получает идентификатор действия и может
узнать результат через API, событие или поддерживаемый механизм адаптера.

## 2. Компоненты

| Компонент | Ответственность |
| --- | --- |
| Identity / Delegation | Пользователи, сервисные идентичности, делегирование и отзыв |
| Agent Registry | Паспорта, версии и владельцы агентов |
| Execution Gateway | Приём запросов, ограничения транспорта, привязка идентичности |
| Action Normalizer | Строгая схема, каноническое действие, описание эффекта |
| Context Resolver | Проверяемые сведения из целевой системы и их свежесть |
| Policy Engine | Детерминированные правила и причины решения |
| Budget Ledger | Атомарные лимиты и резервы, учёт неопределённых исходов |
| Approval Service | Роли согласующих, сроки, ревизии, единственное потребление решения |
| Connector Workers | Внешние вызовы, idempotency, сверка и компенсации |
| Audit / Event Outbox | Долговечные события и надёжная доставка подписчикам |
| Incident Service | Пауза, отзыв, охват инцидента и восстановление |
| Usage / Billing | Счётчики, счета, предоплаченные объёмы и экспорт |

## 3. Жизненный цикл действия

```text
received → validated → evaluating
  ├─ denied
  ├─ deferred → evaluating
  ├─ awaiting_approval → approved / rejected / expired
  └─ authorized

approved / authorized → preflight → reserved → dispatching
  ├─ succeeded
  ├─ failed_definite
  └─ outcome_unknown → reconciling
       ├─ succeeded_reconciled
       ├─ failed_reconciled
       └─ manual_resolution_required
```

В любой точке до отправки возможны отмена, истечение и отзыв. Решение allow
само по себе не означает, что операция была отправлена или завершена.
Компенсация создаёт новое связанное действие с собственной авторизацией.

## 4. Алгоритм допуска и исполнения

1. Проверить транспорт, подпись/токен, организацию, пространство, среду и агента.
2. Ограничить размер запроса и частоту; отвергнуть неизвестный контракт операции.
3. Канонизировать параметры, адресата, ресурс, сумму, валюту и предполагаемый эффект.
4. Разрешить idempotency key в пределах арендатора: одинаковый ключ с другим
   содержимым означает конфликт, а не новое исполнение.
5. Получить обязательный контекст. Входные сведения агента не становятся доверенными.
6. Применить иерархию правил; сохранить решение, версии и основание.
7. При согласовании сохранить неизменяемую ревизию и отправить уведомление через outbox.
8. Перед отправкой повторно проверить паузу, отзыв, актуальность правил и полномочий.
9. Перечитать ресурс/ETag там, где это требуется; изменившиеся условия требуют переоценки.
10. В одной локальной транзакции зарезервировать бюджет и право однократного исполнения.
11. Передать воркеру сохранённый объект, не повторно присланные агентом параметры.
12. Исполнить с провайдерским ключом идемпотентности или оговорённой стратегией.
13. Зафиксировать результат, расход резерва и событие; при неопределённости начать сверку.

Атомарность БД GhostOS не распространяется на внешний API. Переход между
`dispatching` и внешним результатом требует обработки падения процесса.
Для адаптера без upstream-idempotency или надёжной сверки повтор может быть
запрещён. Универсальная гарантия exactly-once не заявляется.

## 5. Привязка подтверждения

Approval относится к хешу канонического объекта, содержащего:

`organization + workspace + environment + agent + delegator + operation_version
+ target_connection + resource_ids + exact_arguments + resource_version
+ policy_version + expires_at + nonce`.

Хеш и подписанный receipt не заменяют проверку полномочий. Исполнитель проверяет
их источник, аудиторию, срок, отзыв и однократное потребление. Несовпадение любого
значимого поля создаёт новую ревизию. Секреты не включаются в экспортируемый объект.

Для операции, состояние ресурса которой нельзя атомарно проверить и изменить,
в контракте фиксируется остаточный риск. Такая операция может иметь меньший
уровень автономности; интерфейс не выдаёт её за полностью условную транзакцию.

## 6. Модель данных

Сущности: organizations, workspaces, environments, users, role_bindings,
agents, delegation_grants, connections, credential_refs, operation_contracts,
policy_bundles, policy_versions, actions, action_revisions, decisions,
approval_requests, approval_votes, budget_accounts, budget_reservations,
execution_attempts, reconciliation_cases, incidents, audit_events,
event_outbox, usage_events, billing_accounts, retention_policies.

Организация/пространство/среда обязательны в ключах и проверках доступа.
Внешний идентификатор сам по себе не уникален между клиентами. Секреты живут
в хранилище секретов; БД хранит ссылки и метаданные. Изменения аудита выполняются
добавлением событий, а не перезаписью прошлого результата.

Уникальные ограничения: tenant-scoped idempotency, однократное использование
approval, переход состояния с ожидаемой версией. Счётчики бюджета используют
транзакционный ledger; кеш не является источником истины для денежных ограничений.

## 7. Публичный контракт API

Предлагаемая поверхность, не готовый SDK:

```text
POST /v1/actions                  создать намерение и получить состояние
GET  /v1/actions/{id}             решение, согласование, результат
POST /v1/actions/{id}/cancel      отменить ещё не отправленное действие
POST /v1/approvals/{id}/decisions подтвердить конкретную ревизию
POST /v1/agents/{id}/pause        запретить новые отправки
POST /v1/delegations/{id}/revoke  отозвать полномочия
GET  /v1/connections/{id}/coverage прочитать область контроля
POST /v1/policies/simulate        проверить правило без внешнего действия
GET  /v1/audit-events             получить разрешённую историю
```

Создание действия поддерживает Idempotency-Key. Повтор запроса возвращает
существующий результат. Вебхуки подписаны, имеют event_id, версию схемы,
повторы с ограничением и документированный порядок; потребители подавляют дубли.
API и SDK не требуют конкретного провайдера LLM.

## 8. Режимы размещения

- **Managed Cloud:** управление и исполнение у оператора продукта, изолированные арендаторы.
- **Hybrid:** управление в SaaS, исполнитель и секреты в сети клиента;
  минимальные редактируемые сведения о действиях передаются в управление.
- **Dedicated:** выделенная установка с оговорёнными обновлениями и эксплуатацией.

В гибриде локальные политики подписаны и имеют срок. Для отзыва задаётся
максимальная допустимая давность списка отзывов. Если её превышают, чувствительные
операции прекращаются. Для особо критических действий требуется онлайн-проверка;
при разрыве связи она не обходится кешем. Цена доступности и граница отзыва
отражаются в договоре и интерфейсе.

## 9. Стек [предложение]

TypeScript для панели, API и официальных адаптеров; PostgreSQL для состояния,
полномочий и ledger; объектное хранилище для разрешённых экспортов и архива;
KMS / secret manager для ключей; долговечные очереди и постоянно работающие
исполнители для внешних операций и сверки; OpenTelemetry для телеметрии.

Панель может использовать знакомый студии веб-стек. Шлюз и воркеры проектируются
по требованиям нагрузки, сетевого размещения и отказоустойчивости. Их работа
не должна зависеть от жизни HTTP-запроса веб-страницы.

Политики: использовать проверяемый существующий движок (например, Cedar или
OPA) после сравнительной проверки выразимости и эксплуатационных свойств.
Бюджеты и workflow остаются отдельными подсистемами; один движок политик не
реализует автоматически все бизнес-инварианты. Выбор инфраструктурного поставщика
и языка политик пока не утверждён.

## 10. Версионирование и совместимость

Версионируются API, схемы операций, адаптеры, политики и события. Обновление
инструмента с новым эффектом требует повторной классификации и публикации.
Миграции выполняются с совместимостью действующих воркеров; откат релиза не
должен повторно отправлять сохранённые операции.
