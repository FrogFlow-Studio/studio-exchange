# 09. Критерии готовности полного продукта

Автор: Север. 09.11.2026. [предложение] приёмочного контракта.

Документ определяет, что означает «готовый коммерческий продукт». Это не
предложение урезанной версии. Концепция не считается реализацией, а прохождение
демонстрации не считается проверкой всей системы.

## Продуктовая комплектность

| Область | Условие готовности |
| --- | --- |
| Организации | Пространства, среды, роли, приглашения, отзыв и передача управления работают сквозным сценарием |
| Агенты | Идентичность, владелец, делегирование, срок и пауза обязательны |
| Политики | Визуальная/декларативная настройка, версии, тесты, согласованная публикация |
| Согласования | Точный эффект, права, сроки, эскалация, исправление и защита от повторного применения |
| Исполнение | Durable state, дубли, бюджеты, внешний результат и неопределённый исход |
| Интеграции | Утверждённый поддерживаемый каталог, контракт каждой операции и матрица покрытия |
| Инциденты | Приостановка области, отзыв, сверка, восстановление и история |
| Агентства | Несколько клиентов, изоляция, шаблоны, клиентский доступ и передача |
| Размещение | Рабочий SaaS и документированный гибрид; выделенная установка по отдельной приёмке |
| Коммерция | Подписка, ограничения, предсказуемый счёт, экспорт и выход |
| Эксплуатация | Дежурство по проданным условиям, мониторинг, резервирование и восстановление |
| Документация | API/SDK, ограничения, подключение, безопасность, поддержка и статус-сервис |

Полнота не означает поддержку любого сервиса мира. Полноценный продукт имеет
законченный цикл работы и честно ограниченный опубликованный каталог.

## Испытания инвариантов

Обязательны проверки настоящего пути «агент → шлюз → провайдер → подтверждённый результат».
Mock-тесты полезны для отдельных условий, но не заменяют подтверждение адаптера.
Испытания выполняются на принадлежащих студии или явно разрешённых тестовых
средах, без реальных платежей и клиентских последствий вне согласованного теста.

| Сценарий | Ожидаемое доказательство |
| --- | --- |
| Обычная разрешённая операция | Во внешней системе ровно ожидаемый эффект и совпадающая история |
| Явный запрет | Вызов не достигает внешнего endpoint, сохранена причина |
| Неизвестный инструмент/метод | Отказ до исполнения, включая MCP resources/prompts вне политики |
| Подмена после approval | Изменённый ресурс, получатель, сумма или среда не исполняются |
| Параллельные запросы | Общий лимит и единственное потребление approval не обходятся |
| Дробление операции | Несколько частей расходуют общий применимый бюджет |
| Повтор от агента | Тот же action возвращает существующее состояние |
| Падение до/после внешнего вызова | Нет слепого повторного эффекта; состояние восстановлено или отмечено неизвестным |
| Тайм-аут провайдера | Сверка результата и удержание соответствующего резерва |
| Смена состояния ресурса | Новая проверка предусловий; остаточные гонки документированы |
| Отзыв и пауза | Очередь не отправляет новые запрещённые операции; in-flight показаны отдельно |
| Потеря связи в гибриде | Выполняется выбранная политика свежести, не бесконтрольное продолжение |
| Чужое пространство | Нет доступа через API, поиск, экспорт, очередь, кеш и storage |
| Обновление адаптера | Новые эффекты не наследуют старые права без проверки |
| Restore из бэкапа | Внешние эффекты сверяются до возобновления спорных операций |

Для адаптера публикуется набор пройденных сценариев, версии и известные ограничения.
Нулевой провал в конечном тестовом наборе не доказывает отсутствие всех уязвимостей.

## Приёмка пользовательского опыта

Владелец процесса способен объяснить: что агенту разрешено; когда он требует
человека; как остановить новые действия; какие операции уже могли исполниться;
как выяснить исход и кому обратиться. Если интерфейс скрывает эти ответы,
техническая реализация сама по себе не даёт готового продукта.

Согласующий видит точный эффект без необходимости читать исходный JSON.
Разработчик при необходимости получает полный разрешённый технический контекст.
Критические данные не исчезают за обрезанным текстом, цветом или мобильной компоновкой.

## Производительность и эксплуатация

Профили включают обычную нагрузку, всплеск, один шумный клиент, очереди
согласований, массовую сверку и деградацию внешних API. Измеряются p95/p99,
ошибки, стоимость, рост БД, время восстановления и возраст неизвестных результатов.

Нужны runbooks, проверенное восстановление, ротация ключей, тест обновления
несовместимого API и независимая проверка границ доступа. Условия SLA ограничены
реально обеспеченной эксплуатацией. Маркетинговые цифры берутся из измерений.

## Коммерческая приёмка

Счёт воспроизводится из usage ledger. Повторы не создают двойную оплату.
Перерасход возможен только на опубликованных условиях. Проверены отмена,
экспорт, отзыв интеграций, удаление и действия при неуспешной оплате подписки.

Цена покрывает измеренную нагрузку и сопровождение. Корпоративные требования
оцениваются отдельно. Нельзя продавать обязательства, за которые никто не отвечает.

## Классы блокирующих дефектов

- Обход авторизации, изоляции или точного согласования.
- Необъяснимый внешний эффект или опасный повтор после неопределённого исхода.
- Неверный денежный/накопительный лимит.
- Утечка секретов либо клиентских данных в чужую область.
- Потеря истории, позволяющая принять уже совершённое действие за неотправленное.
- Интерфейс или документация обещают более сильную гарантию, чем обеспечивает адаптер.

проверки и дата публичного запуска. Документы дают предмет для этих решений,
но не принимают их за Якова.
